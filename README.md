# Deribit index prices

Сервис из двух частей:

1. **Сборщик** — Celery-задача, которая раз в минуту забирает с биржи Deribit индексные цены
   `btc_usd` и `eth_usd` и сохраняет в PostgreSQL тикер, цену и UNIX-время.
2. **API** на FastAPI для чтения сохранённых данных.

Стек: Python 3.12+, FastAPI, SQLAlchemy 2 (async), asyncpg, Alembic, Pydantic v2, aiohttp,
Celery + Redis, PostgreSQL 16, Docker Compose.

---

## Быстрый старт (Docker)

Нужны Docker и Docker Compose v2.

```bash
cp .env.example .env
docker compose up --build
```

В `.env` заполните свои значения. Для compose хосты должны совпадать с именами сервисов:
`DB_HOST=db`, `REDIS_HOST=redis`. Учётка `DB_USER` / `DB_PASS` / `DB_NAME` будет создана
в контейнере PostgreSQL автоматически при первом запуске.

Поднимутся четыре контейнера:

| Сервис   | Что делает                                                         |
|----------|--------------------------------------------------------------------|
| `db`     | PostgreSQL 16, данные в volume `pgdata`                            |
| `redis`  | брокер сообщений для Celery                                        |
| `api`    | прогоняет миграции Alembic и запускает uvicorn на `:8000`          |
| `worker` | Celery worker со встроенным beat, опрашивает биржу каждые 60 секунд |

Проверка:

```bash
curl http://localhost:8000/health
curl "http://localhost:8000/prices/latest?ticker=btc_usd"
```

Swagger UI: <http://localhost:8000/docs>. Первая цена появится примерно через минуту после старта
воркера (первое срабатывание beat происходит через интервал, а не сразу).

Остановить и удалить данные: `docker compose down -v`.

## API

Все методы — `GET`, у всех обязательный query-параметр `ticker` (`btc_usd` | `eth_usd`).
Неизвестный тикер или отсутствие параметра — `422`.

| Метод                   | Описание                                   | Доп. параметры                               |
|-------------------------|--------------------------------------------|----------------------------------------------|
| `/prices`               | все сохранённые цены по тикеру             | —                                            |
| `/prices/latest`        | последняя цена (`404`, если данных ещё нет) | —                                            |
| `/prices/filter`        | цены за период                             | `date_from`, `date_to` — UNIX timestamp, сек |

Для `/filter` нужен хотя бы один из `date_from` / `date_to`; обе границы включительные;
`date_from > date_to` — `422`.

Формат элемента ответа:

```json
{"ticker": "btc_usd", "price": 83570.87, "timestamp": 1791979544}
```

Примеры:

```bash
curl "http://localhost:8000/prices?ticker=eth_usd"
curl "http://localhost:8000/prices/latest?ticker=btc_usd"
curl "http://localhost:8000/prices/filter?ticker=btc_usd&date_from=1791979000&date_to=1791982600"
```

## Локальный запуск без Docker

Нужны Python 3.12+, PostgreSQL и Redis (их проще всего взять из того же compose:
`docker compose up db redis`).

```bash
python -m venv .venv
.venv/Scripts/activate            # Linux/macOS: source .venv/bin/activate
pip install -r requirements-dev.txt

cp .env.example .env
# в .env указать свои значения, хосты для локального запуска:
#   DB_HOST=localhost
#   REDIS_HOST=localhost

alembic upgrade head
uvicorn app.main:app --reload                                    # API
celery -A app.worker.celery_app:celery_app worker --beat -l INFO # сборщик (отдельный терминал)
```

На Windows Celery-воркер стартует с `--pool=solo`.

Разовый запуск сбора без beat (удобно для отладки):

```bash
python -c "from app.worker.tasks import fetch_prices; print(fetch_prices())"
```

## Тесты и линтер

```bash
pytest
ruff check app tests && ruff format --check app tests
```

Тесты не требуют PostgreSQL, Redis и сети: БД подменяется на in-memory SQLite,
биржа — на локальный `aiohttp` тест-сервер. Покрыты клиент Deribit (маппинг ответа, ошибки
API/HTTP/таймаут), сборщик (частичные сбои), DAO (сортировка, границы диапазона) и все три
эндпоинта (включая валидацию `ticker` и дат).

│   ├── dao.py               #   PriceDAO — запросы к БД
│   ├── dependencies.py      #   Depends: сессия, DAO, типы query-параметров
│   └── router.py            #   HTTP-эндпоинты

│   ├── deribit.py           # aiohttp-клиент биржи

│   └── price_collector.py   # сбор цен: клиент → DAO
├── worker/

Поток данных строго в одну сторону:

```
HTTP → router → DAO → БД              (чтение)
Celery beat → task → PriceCollector → DeribitClient → DAO → БД   (запись)
```

## Design decisions

**Модуль на сущность, а не на слой.** Всё, что относится к ценам (модель, схема, DAO,
зависимости, роутер), лежит в `app/prices/`. Новая сущность — новая папка с тем же набором
файлов. Роутер не знает про SQLAlchemy, DAO не знает про HTTP.

**DAO не коммитит.** `BaseDAO` делает только `flush()`; границы транзакции держит вызывающий
слой: для HTTP это зависимость `get_session` (одна сессия на запрос, коммит/rollback в одном
месте), для Celery — сама задача. Так несколько операций DAO можно объединить в одну транзакцию,
а сборщик пишет цены всех тикеров атомарно: либо весь снимок, либо ничего.

**DAO — обычный класс с сессией в конструкторе**, а не набор `classmethod`. Собирается через
`Depends`, в тестах подменяется одной строкой. Зависимости и типы query-параметров живут в
`dependencies.py` модуля, роутер только объявляет ручки.

**Нет глобального состояния.** Единственные объекты уровня модуля — `settings`, `engine`,
`session_factory`, `logger`, `celery_app` и `router`: это конфигурация и фабрики, а не
изменяемое состояние. Клиент биржи, сборщик и DAO создаются на каждый запрос/задачу и получают
зависимости явно.

**Celery + Redis.** Периодичность задаёт Celery beat (`FETCH_INTERVAL_SECONDS`). Redis выбран
как самый лёгкий брокер; RabbitMQ был бы оправдан при сложной маршрутизации, которой тут нет.
Задаче выставлен `expires`, равный интервалу: если воркер лежал десять минут, накопившиеся
задачи протухают, а не выполняются пачкой с одинаковой «текущей» ценой. Beat запущен внутри
воркера (`--beat`) ради простоты; при масштабировании на несколько воркеров beat выносится в
отдельный контейнер, чтобы не дублировать задачи.

**Async внутри Celery.** Celery синхронный, а клиент и ORM асинхронные. Задача выполняет
`asyncio.run(...)` и создаёт для себя отдельный engine с `NullPool`: соединения asyncpg
привязаны к event loop, и пул из API-процесса переиспользовать нельзя. Альтернатива — отдельный
синхронный engine на psycopg только для воркера — означала бы два набора кода доступа к БД.

**aiohttp-клиент как async context manager.** Одна `ClientSession` на цикл опроса, а не на
запрос: так сессия переиспользует соединение для обоих тикеров и гарантированно закрывается.
Ошибки клиента описаны в `services/exceptions.py` как иерархия: базовый `DeribitError` и три
подкласса (транспорт/таймаут/не-200, JSON-RPC `error` с кодом, неожиданная форма ответа).
Сборщик ловит базовый класс и не знает про внутренности aiohttp; подклассы нужны логам и тестам.

**Один тикер упал — остальные сохраняются.** `PriceCollector` логирует ошибку и пропускает
тикер; если не получен ни один — пишет warning и ничего не сохраняет. Ретраи не делаются: через
минуту beat запустит задачу снова, а «догонять» пропущенную минуту старой ценой бессмысленно.

**Одно время на весь снимок.** Timestamp берётся один раз до опроса, чтобы цены BTC и ETH в
одном цикле имели одинаковое время и их можно было сопоставить. Храним `BIGINT` секунд, как
требует ТЗ; `price` — `NUMERIC(20, 8)`, а не `FLOAT`, чтобы не накапливать ошибки округления.
В JSON цена отдаётся числом, а не строкой, так удобнее клиентам.

**`ticker` — `Enum`, а не произвольная строка.** Запрос по несуществующему тикеру получает `422`
с понятным сообщением, а не пустой список; список допустимых значений виден в Swagger. В БД
при этом хранится строка, чтобы добавление тикера не требовало миграции.

**Индекс `(ticker, timestamp)`.** Все три метода API фильтруют по тикеру, два — ещё и по
времени; «последняя цена» — это обратный проход по тому же индексу с `LIMIT 1`.

**Settings без готовых URL.** В `.env` лежат только хост, порт, пользователь и пароль; строки
подключения к БД и брокеру собираются свойствами `Settings`. Так одни и те же переменные
инициализируют контейнер PostgreSQL и приложение, и пароль не дублируется в двух местах.

**Фильтр по дате — UNIX timestamp, границы включительные.** Хранение и API говорят на одном
языке, клиент не зависит от часовых поясов сервера. Проверка «хотя бы одна граница и
`date_from <= date_to`» — два `if` в роутере с ответом `422`.

**Миграции прогоняет контейнер `api` при старте.** Для одного инстанса это проще отдельного
init-контейнера; воркер стартует после `api`, поэтому таблица к его первому запуску уже есть.

**Тесты без инфраструктуры.** SQLite in-memory вместо PostgreSQL и локальный aiohttp-сервер
вместо биржи позволяют гонять тесты за секунду в любой среде. Единственная уступка SQLite —
`BigInteger().with_variant(Integer, "sqlite")` для первичного ключа; в PostgreSQL остаётся
`BIGSERIAL`, что видно в миграции.

**Что бы сделал дальше.** Уникальный индекс `(ticker, timestamp)` с `ON CONFLICT DO NOTHING`
против дублей при двух beat'ах; пагинацию для `/prices` (данных прибавляется 2880 строк в день);
ретеншн старых записей; метрики возраста последней цены для алертинга.
